# Finale Q&A sheet

Short, honest answers. Numbers come from `state.md`; do not round them up.

**Is any of this real data?**
Our LightGBM benchmark is trained and scored on India's real HMIS health data (district-month):
WAPE 0.871 vs 1.078 for the naive baseline on a held-out window, 19% better. That is not the model
the app serves (see the next question). The Nashik facility list is real. The weekly stock
ledger the demo runs on is synthetic, generated by a sealed generator, because facility-level stock
data is not public. The 6% stock-out reduction comes from a replay on that synthetic ledger.

**How accurate is the photo reading?**
On 206 rendered register lines in four scripts, Gemini read the quantity right 100% of the time and
the medicine 98.1%. Those are rendered text, not real handwriting photos; real-photo accuracy is
the first thing a pilot measures. Every photo read is confirmed by the nurse before it is saved.

**What if the forecast is wrong?**
Nothing moves without an officer approving it, and every forecast shows a range (p10-p90) and a
probability, not a single number. The served forecast is lag-1 naive because it beat LightGBM on
the most recent weeks; we pick the model by measurement, not by preference. Next week's demand is the
facility's own use, read from two of its WhatsApp counts a day or more apart; until it has those, last
ledger week's use carried forward (the facility page says which, with the date). So a surge in use
raises the risk and the transfer drafts. Deliveries between two counts are not added back yet, so use
is under-read across a restock. Calibration of the stock-out probability has not been measured.

**Is it really on Google Cloud?**
Yes: Cloud Run in Mumbai, with Firestore for live stock, BigQuery for history, Pub/Sub carrying
WhatsApp messages to the backend, Cloud KMS signing every transfer order, Secret Manager for the
Gemini key and Vertex AI embeddings for medicine names, all provisioned with Terraform. For the demo,
sign-in is a demo picker and WhatsApp is the in-app simulator; Firebase Auth and Twilio are wired
in the code and are the next configuration step for a pilot.

**Where is Google AI used?**
Gemini reads register photos (live), Chirp 2 transcribes voice notes and detects the language
(live), Vertex AI embeds medicine names in 7 scripts (live), Gemini adds a guarded note to agent
answers (live), OR-Tools solves the transfers (live). Cloud Translate / Text-to-Speech for alerts are
wired in cloud mode. The agent picks its tools by rule, so it can never be talked into an action;
Gemini then adds one or two plain-language sentences to its answer, and that note is dropped if it
adds a number the tools did not produce or mentions approving or sending.

**Can the AI approve or send anything?**
No. The agent's tool list has no approve or send tool; we test this by name inspection and with a
prompt-injection attempt. Only a signed-in officer, within their jurisdiction, can approve.

**Privacy?**
Phone numbers are stored hashed. The public view shows district totals only, never a facility
identifier, and a test enforces that. In federation, states share model updates and summary statistics,
not rows; it ties local-only accuracy. The connected demo runs two state nodes as separate processes on
one machine. The scored runs add no noise, so we
claim no differential privacy.

**Why are almost all facilities short of calcium?**
That is in the real HMIS data: reported calcium-tablet use jumps about 20x in December 2019 and
supply lags behind it. We keep the real data and treat it as what it is, a district-wide gap: when
a medicine's district stock is under two weeks of district demand, no facility can spare any, so
the app sends it to the state as a supply request with a quantity instead of drafting transfers.

**The brief also names beds and staff. Where are they?**
On the same WhatsApp number. A nurse sends `BEDS 4/6` (occupied/total); staff check in by sharing
their location, and a check-in more than 200 m from the facility is flagged, not rejected. The
officer's briefing shows "Beds and staff today": facilities at least 90% full with referral
suggestions to the nearest facility with room, and roles with nobody on site with deputation
suggestions from a facility that can spare someone (OR-Tools CP-SAT). Honest limits: facilities that
have not reported show a generated baseline (labelled on screen), bed counts and posts per facility
are IPHS-style norms because the national directory has neither, and these are suggestions, not
signed orders like transfers.

**Does rebalancing actually help, if total supply is short?**
It spreads scarcity: in the replay, stock-out weeks fall 6% while unmet units stay flat (+0.25%).
It does not create supply. The same forecasts can drive procurement, which is the next step.

**Cost to scale?**
Not measured yet. The serving footprint fits a 512 MB instance for one district (760 facilities).
Per-state GCP projects keep data within the state.

**How does this reach the rest of India?**
Every state is already loaded: the MoHFW facility directory (2016) gives 190,609 facilities in 678
districts of 36 states and UTs. A district goes live with its nurses' WhatsApp numbers. Each state
would get its own Google Cloud project, provisioned by the same Terraform module (planned; today one
project serves the demo). Only Nashik has stock data today: the other districts are listed, not
reporting.

**Could a ministry pilot it within weeks?**
Yes, four weeks: week 1 Terraform and Cloud Build (this deployment took one day), week 2 load one
block's nurse numbers and connect Twilio and Firebase sign-in, week 3 daily reports and real register
photos, week 4 approved transfers and supply requests, compared with a matched block not yet using
it over the same weeks. Real sign-in (Firebase accounts) and a verified contact registry are still
to set up; the demo uses a token picker and derived numbers.

**Beyond India?**
Nothing in the core is India-specific. Another country needs a facility list, its essential-medicines
list (the WHO model list plays the role of India's NLEM) and a language pack; Google's speech and
Gemini models already handle Portuguese, Russian, Chinese and Arabic.

**What would a pilot need?**
One block in Nashik, its nurses' WhatsApp numbers, a few weeks of real register photos to measure
extraction, and an officer to approve transfers. The software is ready for that.

**Why WhatsApp?**
Nurses already use it; a new app is another login and another training. Low-confidence reads get a
one-tap confirmation card instead of a form.

## The judge's hardest questions

**Approve a transfer, then run the solver again. What prevents double allocation?**
Approval counts every transfer approved since the donor's last report: if the donor no longer has
the units, approval is refused (409) and the officer re-proposes. Proposals use the same projected
stock, so approved units are not offered twice. The donor's next WhatsApp report already reflects
the move. Tested in `tests/backend/test_flow_integrity.py`.

**This district has no surplus. Show a neighbouring district supplying it.**
Sign in as State officer, Maharashtra and propose: proposals run state-wide, so Dhule surplus covers
Nashik shortages, and a district officer cannot approve those orders (they touch two districts).
Say plainly that the 15 Dhule facilities carry generated demo stock (mirroring nearby Nashik demand)
for this demo; only Nashik's ledger is part of the evaluation.

**Which model produced this recommendation, and when was its demand data last updated?**
The facility page says, per facility: demand from its own reported counts (with the latest date),
or lag-1 naive from the ledger week (with that date). Stock is live from WhatsApp. Order cards show the
destination's stock date, and say "scenario stock" when it is loaded ledger data, not a nurse's count.

**Show what crosses a state boundary during federation.**
Run `python -m ml.federated.demo`: Maharashtra and Meghalaya start as separate processes, each loading
only its own HMIS files. What crosses: row count, feature sums and sums of squares, then FedProx
weights. The coordinator averages them and writes one model; `GET /public/federated` loads it and shows
its estimate beside actual units for Meghalaya's latest validation month (WAPE 0.90). It is not yet
deployed across projects, and the 4-state experiment ties local-only accuracy.

**Why prefer your solver when total unmet demand increased?**
It does not add supply. The policy the app deploys (at least 10 units, at most 5 donors per need),
replayed over 26 weeks: stock-out weeks -4.9%, unmet units +0.41%, fill rate 67.83% to 67.70%, about
230 transfers a week (`eval/run_replay.py --live`). The unconstrained policy did -6.0% with 570 a week
and nearly three times the driving. It spreads scarcity so fewer facilities run dry; the supply fix is
the state request.

**Show the two facilities receiving the order, then acknowledge receipt.**
Approve on Orders: both facilities get the signed order in the simulator (pick each facility). The
source replies `SENT <code>`, the destination `RECEIVED <code>` (or the officer taps Mark sent, Mark
received). Until `SENT`, the units stay reserved at the source whatever it reports, so the same units
cannot be approved twice; units on their way cannot be sent onward before they arrive.

**Is the agent just keyword matching?**
For the common questions, yes, on purpose: fixed templates over the same tools answer fast and the same
way every time. Anything else goes to Gemini function calling over six read-only functions, each
jurisdiction-checked. An answer is kept only if a function answered and every number in it came from
a function result (or counts one of its lists); a number only the officer typed does not count. Requests to approve or
send never reach a model.

**Are beds and staff only suggestions?**
No longer: an officer approves a referral or deputation, and it becomes a KMS-signed order sent to both
facilities on WhatsApp, like a transfer. Bed and staff numbers per facility type are IPHS-style norms.

**Why does the screenshot say 133 drafts when the README says 77 and 58?**
The Nashik officer's view counts every draft touching Nashik: 77 inside Nashik plus 58 from Dhule after a
state-wide run, less 2 already approved, is 133.

**Why only one backend instance?**
The stock index, reported-use readings, the order lock and the duplicate check live in process memory,
so the backend runs one warm instance (`min=max=1`): correct, and enough for a district. Scaling out
means moving those to Firestore (transactions for the lock and duplicates, a snapshot listener for the
index); the code marks each spot with `shortcut:`.

**Does the live solver use expiry (FEFO) and cold chain?**
The solver supports both (unit-tested), but the live stock reports carry no batch or cold-chain fields
yet, so live orders show one unbatched line. Batches come with the register photo fields in the pilot.

**Why does the federated card show 0 for South Garo Hills (4,57,500 distributed)?**
That district had reported no earlier month of that item, so every lag feature was empty and the
model had nothing to go on (marked * on the card); a state's own model has the same gap. Where history
exists it still undershoots big one-off issues (Ri Bhoi calcium: 54,986 vs 3,99,000): district issues
are lumpy, and one linear model in log space smooths spikes. Overall 0.90 WAPE, the same as each state
alone: federation's value here is keeping rows in their state, not accuracy. Next step: keep a local
output layer per state on the shared weights, and treat "no history" rows with a separate cold-start
rule instead of the regression.
